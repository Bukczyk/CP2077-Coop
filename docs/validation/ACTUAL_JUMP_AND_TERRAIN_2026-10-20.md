One bounded Computer Use Space input in the actual HOST produced a visible
camera rise/fall and native `gamePSMLocomotionStates.Jump` (value 5). JOINER's
original video shows the remote actor taking off, flying, landing and returning
to idle. This tests an actual player input rather than a synthetic movement
replay. Installed source was `6901345`, lower M13/action layer3, unchanged
native runtime/server `9f27bd4` and private32773. No firing or remapping occurred.

Both actual views were recorded for60 seconds after encoder warmup. Coverage,
cadence and unchanged-tool-hash checks pass. Largest tested frame gaps are
84.4 ms HOST and178.7 ms JOINER. Original first-response, airborne, landing and
later-idle samples were reviewed in both videos, with original PTS retained.

JOINER retains548 complete rows for the exact HOST actor10838018 in the selected
window. Three rows select takeoff,12 flight,7 landing and526 idle. Root height
spans1.347014 m from the initial sampled baseline, maximum readback error is

No actor fault or held crouch occurs in this standing check. HOST's existing

observe its own remote actor, so no such HOST observer rows are claimed.

The input-call start timestamp precedes the actual OS/game processing. It must
not be described as measured network latency. This is one local standing jump,
not all jump variants, physical walking, terrain or WAN acceptance.

## Uphill case still fails

An independent headless probe supplies180 continuous samples over3 seconds at
2 m/s horizontal speed. At10% and25% grades, all180 samples remain walking.
At50% grade, the current displacement-based inference produces7 walking,
8 takeoff and165 flight samples, despite a continuous straight ramp rather than
a ballistic jump. This reproduces a renderer limitation from transforms alone;
it does not demonstrate actual engine slope traversal.

Raising the vertical threshold is not a qualified fix: it can hide real low
jumps while leaving other slopes or steps misclassified. A locomotion enum is
also not a verified physical-contact flag. Jump5 was observed, but Default0
alone must not be asserted to mean grounded during every engine mode.

`PlayerPuppet.GetCurrentLocomotionState(player)` is already read on the game
thread by movement diagnostics and is verified by this recording. Metadata
inspection did not establish a callable grounded/contact getter. The existing
read-only source capture can be extended after a specific hook is verified.
No unsupported getter, raw memory offset or synthetic ground flag was added.

## Shared data still to agree

The engine side needs action/locomotion state and position associated with the
same actual observation, plus current-view aim direction when valid. The
current action receipt is the latest arrival, while position is interpolated.
The movement packet's timestamp is generated by the network tick and must not
silently be relabeled as the actual engine capture time.

KyleBuildsAI owns capture eligibility, local pose application and the engine
tests. Bukczyk owns review of the typed delivery/recovery contract. The desired
exchange is engine -> session/server -> observers, scoped to the exact player,
session/entity and epoch. Latest valid state should recover after join/reconnect;
stale or unavailable state must remain explicitly unknown. Direction/units,
sample association, freshness and handling of unsupported locomotion modes need
agreement. This is a requirement proposal for the existing PR18 review, not an
implemented protocol extension or a new networking design.

The combined acceptance test must distinguish walking up a ramp/steps from a
real jump, align action changes with the rendered position and aim in the
source camera direction. Record both actual views and source/observer timing,
then repeat after reconnect. Engine pose/resource and diagnostic work can
continue before that delivery contract is accepted.
